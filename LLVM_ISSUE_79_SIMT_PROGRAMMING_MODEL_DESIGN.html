1. 文档目的

本文说明 LLVM Issue #79 的需求背景、现行编程模型、目标编程模型、对软件栈的冲击、编译器需要完成的工作，以及当前和目标汇编形态。

Issue #79 不是增加一条 intrinsic 或修复一条指令编码，而是一次跨越 Clang、LLVM IR、MachineIR、Blockify、MC、对象格式和运行模型的 SIMT 编程模型升级。其目标是让开发者继续编写普通 C++ for、if、else、break 和 continue，由编译器自动构造 predicate、EXEC mask、重汇聚和 Tile region 操作。

本文严格区分：

  1. 当前可用的 PTO/Linx 0.58 模型；
  2. PTO-SPEC #189 提议但尚未冻结的 0.59 模型；
  3. 不依赖最终指令编码、现在即可开展的编译器工作；
  4. 必须等待 ISA 合同确定后才能完成的工作。

本文中的 0.59 汇编均为结构示意，除非明确标记为现行 0.58 指令，否则不得作为已批准的编码或语义实现。

1.1 整体编译路线摘要

Issue #79 的整体路线可以概括为：开发者继续使用普通 C/C++ for、if、 else、break 和 continue 描述逐元素计算；LLVM 首先通过 uniformity analysis 判断条件是 uniform 还是 varying，而不是先把所有 predicate 都转成 标量。uniform 条件可以进入普通标量控制域，并在 ISA 合同正式批准后选择 B.Z、B.NZ 或其最终替代分支形式；varying 条件必须保留为 predicate/EXEC mask，切换到 divergent SIMT lowering，由编译器维护 active mask、saved mask、 if/else/loop 控制帧和 reconvergence 点。Vector 计算体按 element-wise 语义 生成，由当前 EXEC mask 决定哪些 element 产生架构效果；TileOP API 不要求开发者 手写 TileOP 级控制栈或复杂分支。B.SUBVIEW、B.ASSEMBLE、TPARTVIEW、 TileArray 和 TASSEMBLY 只描述 parent Tile、fragment、source region 和 destination assembly session 的数据关系，不承担控制流语义，但必须作为 typed Tile region/session SSA 保留到后端，使 SIMT kernel 可以在不同控制流路径中安全 访问和组装 Tile 数据。

整体流程如下：

普通 C/C++ element-wise 控制流
    |
    v
UniformityAnalysis：区分 uniform / varying
    |
    +-- uniform condition
    |      -> 标量条件
    |      -> 普通 scalar CFG
    |      -> B.Z / B.NZ 或最终批准的替代形式
    |
    +-- varying condition
           -> predicate / condition mask
           -> then_mask = EXEC & condition
           -> else_mask = EXEC & ~condition
           -> compiler-side control frame
           -> divergent body + reconvergence
    |
    v
在当前 EXEC 下生成 element-wise Vector 操作
    |
    v
通过 Subview / TileArray / Assemble 管理 Tile region 和结果组装

其中最重要的边界是：

  1. 不能先把 divergent predicate 压成单个标量。 这样会丢失各 element 的 分支状态；只有被证明为 uniform 的条件才进入普通标量分支。

  2. B.Z/B.NZ 是 uniform scalar branch 的候选入口，不是 divergent mask 控制本身。 截至本文基线，它们仍是 reserved-in-pto，这里只描述编译结构， 不代表指令语义已经冻结。

  3. divergent 控制由编译器维护，不暴露给 TileOP 开发者。 编译器需要跟踪：

    ControlFrame {
  saved_exec;
  remaining_else_mask;
  reconvergence_block;
  loop_break_mask;
  loop_continue_mask;
}

  4. Tile region 与控制栈是正交机制。 Subview/TPARTVIEW 负责读取 parent 的 fragment，TileArray/Assemble/TASSEMBLY 负责构造 destination parent；它们 不执行 if/else，但 region 的覆盖范围、生命周期、重叠关系和 INIT/MIDDLE/LAST 必须由编译器验证和推导。

  5. 应移除的是字符串化 Vector/SIMT body，而不是所有 TileOP inline asm。 linx-vblock-body-asm、body-local ri/vt/vu/vm/vn 和第二套 scalar-import namespace 应迁移到 typed IR/MachineIR；已经符合 ISA 的单条 Vector TileOP、 Cube TMATMUL/TGEMV/TCVT、load/store 以及 region modifier inline asm 可以作为 0.58 兼容路径继续保留，之后再逐步切换到正式 instruction selection。

2. 需求背景

2.1 用户希望保留普通 C++ 控制流

开发者期望编写普通的 element-wise C++：

void piecewise(float *out, const float *x, int n) {
  #pragma clang loop linx_simt(enable) linx_schedule(auto)
  for (int i = 0; i < n; ++i) {
    float value = x[i];

    if (value > 0.0f) {
      if (value > 10.0f)
        out[i] = value * 2.0f;
      else
        out[i] = value + 1.0f;
    } else {
      out[i] = -value;
    }
  }
}

开发者不应该手写：

  • predicate 寄存器编号；
  • EXEC mask 更新；
  • mask 保存和恢复；
  • reconvergence label；
  • 控制栈 push/pop；
  • B.Z / B.NZ；
  • body-local ri/vt/vu/vm/vn 寄存器；
  • 手工展开的 bundle 汇编。

Clang 只表达用户意图，LLVM 在优化后判断循环是否适合 SIMT 化，以及应使用有序执行还是迭代并行执行。

2.2 Tile element 访问不能退化为普通标量地址访问

Tile-view 编程希望具有类似下列源代码：

template <class DstView, class SrcView>
void tile_piecewise(DstView dst, SrcView src) {
  #pragma clang loop linx_simt(enable) linx_schedule(auto)
  for (int i = 0; i < src.size(); ++i) {
    auto value = src[i];
    if (value > 0)
      dst[i] = value + 1;
    else
      dst[i] = -value;
  }
}

这里的 src[i] 和 dst[i] 不是普通可取地址的 C++ 引用，也不应被实现为 Local Tile 与 body-local vector register 之间的 VLOAD/VSTORE 搬运。它们应被编译器识别为：

父 Tile + 当前迭代对应的 region

源操作映射为 B.SUBVIEW，目标操作映射为 B.ASSEMBLE，中间值继续存在于顶层 Tile/region SSA 中。

2.3 为什么现有 0.58 路径不适合继续扩展

当前 LLVM LinxISA 后端已经能识别部分 counted loop、affine memory、reduction、select 和结构化内部 CFG，也能处理一些简单 diamond。但其核心实现仍基于 0.58 的 body-local 执行模型：

普通 LLVM IR
    |
    v
LinxISASIMTAutoVectorize
    |
    +-- 生成 linx-vblock-body-asm 字符串
    +-- 生成 llvm.linx.vblock.launch
    |
    v
PSEUDO_VBLOCK_LAUNCH
    |
    v
LinxISABlockify
    |
    +-- BSTART.MSEQ / MPAR / VSEQ / VPAR
    +-- B.TEXT
    +-- B.IOR 导入 ri0..ri11
    +-- body-local PSEUDO_V_* / v.* 指令
    +-- BSTOP

这种模型存在以下根本限制：

  • body 被序列化为字符串，后续 LLVM pass 看不到真实 CFG 和数据依赖；
  • llvm.linx.vblock.launch 提供第二套最多十二项的 ri* 标量导入命名空间；
  • PSEUDO_V_* 以立即数携带 body-local ri/vt/vu/vm/vn 编号；
  • predicate、EXEC 和 reconvergence 没有完整的 typed IR/MachineIR 表示；
  • Scheduler、Register Allocator 和 verifier 无法可靠跟踪控制 mask 的 use/def；
  • Tile region 被迫通过复制或字符串汇编表达，不能与 LLVM #74 的 region/session 模型组合；
  • MSEQ/MPAR/VSEQ/VPAR 将 body 能力和执行顺序绑在同一个 header 选择中。

Issue #79 要求删除这些架构假设，而不是在它们外面增加新的伪指令名称。

3. 当前 PTO/Linx 0.58 编程模型

3.1 当前架构状态

截至 2026-09-01：

  • PTO-SPEC 正式发布身份仍是 0.58.5；
  • Linx ISA canonical profile 仍是 v0.58；
  • BSTART.MSEQ、BSTART.MPAR、BSTART.VSEQ 和 BSTART.VPAR 属于当前/历史 scheduled body 模型；
  • body 内使用统一 lx64 编码空间，但仍存在每 lane/body-local 的 vt/vu/vm/vn 以及导入的 ri*；
  • 当前架构 EXEC mask 为 p，当前说明使用 V.CMP.* ->p 生成 mask；
  • B.Z 和 B.NZ 只有 PTO 保留编码，状态为 reserved-in-pto，不能视为正式、可移植的已定义指令。

3.2 当前编译器输入形式

当前主要入口是自动向量化识别的普通 LLVM loop，而不是完整的 C++ SIMT pragma 合同。LinxISASIMTAutoVectorize.cpp 根据循环和 body 特征选择生成 scheduled body。

已有实现可以覆盖：

  • canonical counted loop；
  • 部分 affine load/store；
  • 部分整数和浮点算术；
  • select；
  • 简单 reduction；
  • 简单 if-converted diamond；
  • 部分嵌套 mask branch 测试。

但复杂 grouped divergence 会遇到类似：

grouped_layout_requires_exec_mask_save_restore

这表明当前编译器缺少完整的 mask save/restore 和 reconvergence 表示。

3.3 当前 0.58 汇编形态

以下是当前模型的结构示意，不代表某个具体测试的逐字反汇编：

BSTART.MSEQ ...              # 或 MPAR/VSEQ/VPAR
B.TEXT ...
B.IOR a0, ->ri0              # 导入第二层 scalar namespace
B.IOR a1, ->ri1
C.B.DIMI ..., ->lb0
C.B.DIMI ..., ->lb1

v.lw.brg [ri0, lc0.uh<<2, 0], ->vt.w
v.flt vt#1.sw, ..., ->p
B.Z .Lelse                   # 当前仍不能作为已冻结的 0.59 合同
v.fadd vt#1.sw, ..., ->vu.w
v.sw.brg vu#1.uw, [ri1, lc0.uh<<2, 0]
...
C.BSTOP

这个模型中的 ri、vt、vu 和 p 属于 scheduled body 内部状态。Issue #79 的 0.59 目标明确要求不再保留第二套 body-local V/scalar-import 寄存器层级。

4. 目标 PTO/Linx 0.59 编程模型

4.1 单一架构寄存器层级

目标模型只保留一套架构状态：

Main GPR
Predicate P0..P7
Local Tile
Shared Tile
Tile region / generation state
Execution-instance EXEC / reconvergence state

不再存在：

ri0..ri11
vt/vu/vm/vn body-local register IDs
body-local scalar-import namespace
linx-vblock-body-asm 字符串 body

Uniform 值与 varying 值的归属如下：

源语言值 编译器分类 目标表示
循环外不变整数/指针 Uniform numeric Main GPR
Uniform 条件 Uniform boolean 普通 scalar CFG/GPR 条件
每元素数值 Varying numeric Tile/region SSA
每元素条件 Varying boolean PRED32 / EXEC mask
TCMP 产生的 packed predicate Tile Tile data 不能隐式当作 P1..P7/EXEC

4.2 执行顺序与 body 能力解耦

0.59 提案使用正交的执行顺序标记：

B.SEQ
B.PAR

而不是继续使用 MSEQ/MPAR/VSEQ/VPAR 同时表达 body 类别和顺序。

B.SEQ

B.SEQ 是保守、有序的执行模式：

  • 迭代按架构规定顺序提交；
  • 允许 main GPR 写入；
  • 允许 loop-carried scalar recurrence；
  • 允许在不破坏 Tile view 和 precise fault 的前提下进行 scalar lowering；
  • divergent branch 仍必须具有合法的 EXEC 和 reconvergence 状态。

B.PAR

B.PAR 是经证明可以并行的执行模式：

  • 完整 body 不得写普通 main GPR；
  • 动态上不执行的 GPR 写路径也必须在预检中拒绝；
  • GPR 读取使用 region-entry snapshot；
  • varying numeric 不能临时落入普通 GPR；
  • destination region 必须证明不重叠；
  • 普通 loop-carried recurrence 不合法；
  • 未定义的 call、volatile、atomic、alias 或 predicate spill 必须拒绝。

默认策略：

linx_schedule(auto) -> 证明 PAR 合法才选 B.PAR，否则 B.SEQ/标量回退
linx_schedule(seq)  -> 请求 B.SEQ
linx_schedule(par)  -> 必须证明合法，否则稳定诊断

4.3 Predicate、EXEC 和重汇聚

LLVM IR 保留正常 SSA CFG。目标 pass 根据 uniformity 与 CFG 结构插入控制流 marker，而不是让用户显式管理 mask。

概念控制帧：

ControlFrame {
  saved_exec;
  remaining_else_mask;
  reconvergence_block;
  loop_break_mask;
  loop_continue_mask;
}

一个 varying if/else 的概念语义为：

entry_exec = EXEC
then_exec  = entry_exec & condition_mask
else_exec  = entry_exec & ~condition_mask

在 then_exec 非零时执行 then
在 else_exec 非零时执行 else
在 join 处恢复 surviving mask

break 和 continue 不能简单恢复入口 mask，而必须更新 loop live mask、broken mask 和 continue mask。

4.4 Direct Tile region

Tile-view 循环中的第 i 个 fragment 由迭代坐标计算：

offset = base_offset + LinearIterationID(LC) * fragment_size

源读取：

Parent Tile + B.SUBVIEW(offset, fragment size)

目标写入：

Parent working generation + B.ASSEMBLE(offset, parent size, INIT/LAST)

要求：

  • modifier 必须紧邻其拥有的 binder；
  • source snapshot 先于 destination publication；
  • 同一个 parent 的 destination fragment 进入同一个 assembly session/generation；
  • INIT 初始化 parent generation；
  • LAST 结束并发布完整 parent；
  • B.PAR 下默认要求 fragment 互不重叠；
  • fault、replay、rollback、coverage 和 publication 服从 PTO generation 合同。

5. 对软件栈的冲击

5.1 Clang 前端

需要增加或正式化 loop hint：

linx_simt(enable | disable)
linx_schedule(auto | seq | par)

前端职责仅限：

  • 保留普通 C++ CFG；
  • 检查 pragma 拼写和组合；
  • 生成 loop metadata；
  • 对明显不支持的 non-addressable Tile element escape 报错。

前端不能声明某个 loop 已经 B.PAR 合法，最终合法性必须在优化后的 LLVM IR 上证明。

5.2 LLVM IR 与 Analysis

需要：

  • 使用 UniformityAnalysis 区分 uniform/varying；
  • 使用 DominatorTree、PostDominatorTree 和 LoopInfo 寻找 reconvergence；
  • 增加 LinxSIMTControlFlow pass；
  • 保持普通 SSA PHI；
  • 插入 IF/ELSE/IF_BREAK/LOOP/END_CF target marker；
  • 增加 convergence/noduplicate 约束，禁止跨 mask transition 克隆、推测、CSE 或 sinking；
  • 保持 Tile parent、region 和 generation/session 的 typed SSA。

临时 target intrinsic 可采用 Issue #79 提议的结构：

declare {i1, i32} @llvm.linx.simt.if(i32 %condition_mask)
declare {i1, i32} @llvm.linx.simt.else(i32 %saved_mask)
declare i32       @llvm.linx.simt.if.break(i32 %condition_mask,
                                           i32 %broken_mask)
declare i1        @llvm.linx.simt.loop(i32 %broken_mask)
declare void      @llvm.linx.simt.end.cf(i32 %saved_mask)

这些 intrinsic 仅是编译器内部 marker，不代表一一对应的物理指令。

5.3 MachineIR 与寄存器分配

需要增加：

  • PRED32 register class/bank；
  • P0 all-active 常量约束；
  • P1..P7 分配；
  • explicit EXEC uses/defs；
  • IF/ELSE/END_CF/LOOP pseudos；
  • Tile parent/region operands；
  • assembly-session operands；
  • predicate pressure 和嵌套深度检查；
  • 无合法 spill carrier 时 fail closed。

必须删除 0.59 输出中的：

  • body-local ri/vt/vu/vm/vn immediate ID；
  • PSEUDO_V_* 作为第二层寄存器机器模型；
  • VLOAD/VSTORE 形式的 Tile bridge。

5.4 Instruction Selection 与 Blockify

ISel 应把 Tile 算术降低到 typed PSEUDO_TILEOP_*，而不是提前序列化汇编。

Blockify 最终负责：

  1. 发射一个 0.59 scheduled-region header；
  2. 发射 B.TEXT；
  3. 发射经 ISA 批准的 B.SEQ 或 B.PAR；
  4. 发射 dimensions；
  5. 绑定 main GPR、predicate、Local Tile、Shared Tile 和 region/session；
  6. 展开 TileOp bundle；
  7. 将 B.SUBVIEW / B.ASSEMBLE 放在对应 binder 旁边；
  8. 发射显式 BSTOP，或使用下一条 BSTART 作为 bundle boundary；
  9. 保留精确对象身份。

5.5 MC、汇编器和反汇编器

需要支持两种视图：

  • virtual TileOp assembly；
  • physical bundle assembly。

一个 virtual TileOp 必须确定性展开为一个 physical bundle。反汇编只有在物理 bundle 唯一、完整匹配 schema 时才能折叠为 virtual TileOp；以下情况必须打印 physical view：

  • operand 多余或缺失；
  • modifier 顺序错误；
  • bundle 边界不唯一；
  • bundle 从外部 label 进入；
  • schema 匹配存在歧义；
  • 显式默认值与省略默认值不等价。

5.6 对象格式、Linker 与运行模型

0.59 是硬架构边界：

  • 0.58 object 与 0.59 object 不应混链；
  • .note.pto.isa 必须携带精确身份；
  • Linker 必须拒绝不一致的 PTO identity；
  • QEMU、functional model、RTL/cycle model 必须执行同一对象；
  • fault/restart context 必须保存 EXEC、predicate、control-stack、range 和 generation 状态；
  • B.PAR 必须定义内存副作用、冲突和 fault arbitration；
  • assembly publication 必须具有原子 parent 可见性。

5.7 TileOP API

TileOP 需要：

  • 提供 non-addressable Tile element/region view；
  • 保持普通 C++ for/if body；
  • 将 TPARTVIEW/range view 映射到 compiler-recognized region SSA；
  • 将 TASSEMBLY/destination slots 映射到 assembly session；
  • 不要求用户指定 predicate、EXEC 或物理寄存器编号；
  • 不使用 inline assembly 隐藏需要 LLVM 分析的控制流；
  • 对固定 TileOp bundle 可继续使用生成的低层 carrier，但控制流和 region 生命周期必须由编译器看见。

6. 编译器实现方案

6.1 阶段一：清理 typed body

目标是替换：

linx-vblock-body-asm
llvm.linx.vblock.launch 的十二个 ri* slots
PSEUDO_V_* immediate register IDs

保留真实 LLVM CFG 和 MachineBasicBlocks。第一阶段可以继续发射 0.58 backend 形式用于兼容测试，但内部表示必须不再依赖字符串。

建议新增/重构：

llvm/lib/Target/LinxISA/LinxISASIMTBody.cpp
llvm/lib/Target/LinxISA/LinxISASIMTBody.h
llvm/lib/Target/LinxISA/LinxISASIMTBodyVerifier.cpp

也可以在现有 LinxISASIMTAutoVectorize.cpp 中先抽离数据结构，再逐步拆文件，避免一次性大重写。

6.2 阶段二：SIMT 控制流标注

新增 LinxSIMTControlFlow：

  1. 找到已选择的 SIMT loop；
  2. 运行 UniformityAnalysis；
  3. 保留 uniform branch；
  4. 对 varying branch 找唯一 reconvergence；
  5. 插入 IF/ELSE/END_CF marker；
  6. 对 loop exit 插入 IF_BREAK/LOOP marker；
  7. 对 irreducible CFG、多个不明确 join 和异常边拒绝；
  8. 标记 convergence boundary，防止后续 pass 非法移动。

可以参考 AMDGPU SIAnnotateControlFlow.cpp 的算法结构，但不能复制 AMD wave64、SGPR 或具体指令语义。

6.3 阶段三：Predicate/EXEC MachineIR

定义逻辑层伪指令，例如：

PSEUDO_SIMT_IF
PSEUDO_SIMT_ELSE
PSEUDO_SIMT_END_CF
PSEUDO_SIMT_IF_BREAK
PSEUDO_SIMT_LOOP
PSEUDO_SIMT_BRANCH_ZERO
PSEUDO_SIMT_BRANCH_NONZERO

每条伪指令必须显式声明：

  • predicate input/output；
  • implicit EXEC use/def；
  • control side effect；
  • convergent/barrier 属性；
  • branch target；
  • saved mask live range。

在 ISA 合同冻结前，这些伪指令不得绑定自创的物理 encoding。

6.4 阶段四：Tile region lowering

复用 LLVM #74 的 region/session 思路，不建立第二套表示。

建议内部值：

TileParentValue
TileSubviewValue(parent, offset, size)
TileAssemblySession(parent, parent_size)
TileAssemblySlot(session, offset, fragment_size, init, last)

ISel 输出应能表达：

PSEUDO_TILE_SUBVIEW parent, base, offset, size
PSEUDO_TILEOP_TADD dst_region, src_region_a, src_region_b
PSEUDO_TILE_ASSEMBLE session, dst_region, base, offset, parent_size, init, last

Blockify 再将 region modifier 放到 binder 旁边。

6.5 阶段五：B.SEQ / B.PAR 分析

建立 whole-body effect summary：

WritesMainGPR
ReadsMainGPR
HasLoopCarriedRecurrence
HasUnknownCall
HasVolatile
HasAtomic
HasUnknownAlias
HasOverlappingDestinationRegion
HasPredicateSpill
HasIrreducibleCFG
HasUnsupportedFaultingEffect

选择逻辑：

if policy == seq:
  select SEQ if SIMT lowering is otherwise legal

if policy == par:
  require complete PAR proof, otherwise diagnose

if policy == auto:
  select PAR only with complete proof
  otherwise select SEQ
  otherwise leave scalar

必须产生结构化 optimization remarks，说明：

  • 为什么选择 PAR；
  • 为什么回退 SEQ；
  • 哪条指令或哪类 effect 阻止 PAR；
  • 是否因为目标 ISA 身份缺少必要控制指令而放弃 lowering。

6.6 阶段六：MC 与发布闭环

等待 PTO-SPEC #189 和 Linx ISA 0.59 冻结后：

  • 增加真实 B.SEQ / B.PAR；
  • 增加真实 B.Z / B.NZ 或最终批准的替代形式；
  • 增加 EXEC save/update/restore carrier；
  • 增加 reconvergence carrier；
  • 更新 Blockify expansion；
  • 更新 assembler/disassembler；
  • 更新 object note 和 linker identity check；
  • 更新 QEMU、模型和 release pins；
  • 删除 0.59 lane 中旧的 MSEQ/MPAR/VSEQ/VPAR 和 body-local V 假设。

7. 汇编设计

7.1 现行 0.58 汇编

现行 0.58 仍使用 scheduled body header 与 body-local 指令。结构上类似：

BSTART.MSEQ ...
B.TEXT ...
B.IOR a0, ->ri0
B.IOR a1, ->ri1
C.B.DIMI 32, ->lb0
C.B.DIMI 1,  ->lb1

v.lw.brg [ri0, lc0.uh<<2, 0], ->vt.w
v.flt vt#1.sw, zero, ->p
v.csel p, vt#1.sw, ..., ->vu.w
v.sw.brg vu#1.uw, [ri1, lc0.uh<<2, 0]
C.BSTOP

这是当前软件栈可以识别的旧模型，不是 Issue #79 的最终目标。

7.2 目标 0.59 物理结构示意

PTO-SPEC #189 期望的结构大致为：

BSTART.<scheduled-region> ...       # 最终 header 名称/编码待 ISA 冻结
B.TEXT ...
B.SEQ                              # 或 B.PAR；编码和位置待冻结
B.DIM ..., ->lb0
B.DIM ..., ->lb1

# 直接绑定顶层 Tile/GPR/predicate，不导入 ri/vt/vu/vm/vn
...
BSTOP

需要强调：B.SEQ 和 B.PAR 当前尚无正式 0.59 encoding，以上只能作为目标结构。

7.3 Source subview 的目标 bundle

假设一个 TileOp 从 parent Tile 中读取当前迭代的 fragment：

BSTART.VEC TADD, FP32
B.DATR ...
B.DIM ..., ->lb0
B.DIM ..., ->lb1

B.IOT t#parent_a, mask=1111
B.SUBVIEW 0, base_a, offset_a_128B, fragment_size_code

B.IOT t#parent_b, mask=1111
B.SUBVIEW 0, base_b, offset_b_128B, fragment_size_code

B.IOT mask=1111, last, ->t#tmp<fragment_size_code>

这里沿用当前 0.58 B.SUBVIEW 已定义的核心概念：

  • RegSrc/base 和立即数 offset 共同确定 region 起点；
  • offset 单位为 128 B；
  • size code 表示 fragment 大小；
  • modifier 紧邻它所修饰的 source binder。

最终 0.59 是否调整顶层 Tile 拼写、binder 形式或字段位置，必须服从 PTO-SPEC #189 的最终合同。

7.4 Destination assemble 的目标 bundle

将 fragment 写入 parent generation：

BSTART.VEC TADD, FP32
B.DATR ...
B.DIM ..., ->lb0
B.DIM ..., ->lb1

B.IOT t#src_a, mask=1111
B.IOT t#src_b, mask=1111
B.IOT mask=1111, last, ->t#parent_working<fragment_size_code>
B.ASSEMBLE INIT, LAST, base_dst, offset_dst_128B, parent_size_code

语义：

  • INIT=1：建立 parent working generation，并携带 parent size；
  • INIT=0：继续向已存在 generation 写 fragment；
  • LAST=1：结束本次 assembly session，并按合同发布 parent；
  • offset 单位为 128 B；
  • B.PAR 下多个迭代的 destination fragment 默认必须不重叠；
  • compiler 应推导 INIT/LAST，而不是要求普通 C++ 用户填写。

7.5 Divergent branch 的目标结构示意

Issue #79 给出的逻辑结构可表达为：

P.CMP ... ->P1               # 比较指令名称待 ISA 冻结
EXEC.SAVE.AND P1 ->P2        # EXEC carrier 待 ISA 冻结
B.Z .Lelse                   # 当前仅 reserved-in-pto

# then body
...

EXEC.ELSE P2                 # 待 ISA 冻结
B.Z .Ljoin

.Lelse:
# else body
...

.Ljoin:
EXEC.RESTORE P2              # 待 ISA 冻结

这些名称仅说明编译器需要的语义操作：

  1. 产生 predicate；
  2. 保存入口 EXEC；
  3. 切换 then mask；
  4. 测试是否有 active instance；
  5. 切换 else mask；
  6. 在 join 恢复 surviving mask。

当前不能直接实现这些物理指令，因为以下内容尚未确定：

  • predicate compare mnemonic；
  • EXEC 宽度与物理载体；
  • save/and/else/restore 的指令形式；
  • B.Z/B.NZ 测试的对象；
  • reconvergence stack 的架构状态；
  • fault/restart 时的保存恢复行为。

7.6 Virtual TileOp 汇编

目标工具链还需要允许开发者或生成器书写单条 virtual TileOp，例如概念上的：

TADD dst, src_a, src_b, schedule=par, subview_a=..., assemble_dst=...

assembler 根据生成的 TileOp schema 将其唯一展开成一个 physical bundle。具体 public syntax 尚未冻结，不应由 LLVM 单独决定。

需要满足：

  • 一个 virtual TileOp 对应一个 physical bundle；
  • virtual assembler 与 compiler pseudo expansion 生成完全相同的字节；
  • disassembler 只折叠唯一、完整、无歧义的 bundle；
  • malformed 或 externally entered bundle 保留 physical view；
  • omitted default 与 explicit zero 的规则必须由 schema 明确定义。

8. 当前 ISA 缺口

8.1 已存在，可先接入

以下物理基础已经存在：

  • B.SUBVIEW；
  • B.ASSEMBLE；
  • INIT/LAST；
  • 128 B offset 单位；
  • Tile size code；
  • assembler/parser/disassembler 的基础实现；
  • MC 正向、反向和非法编码测试。

因此 Tile region typed lowering、modifier 邻接、range 验证和 assembly session 分析可以先做。

8.2 旧模型存在，但 0.59 语义不同

以下形式在 0.58 中存在或被保留：

BSTART.MSEQ
BSTART.MPAR
BSTART.VSEQ
BSTART.VPAR

它们不能直接被解释为 0.59 的 B.SEQ/B.PAR。0.59 要求执行顺序标记与 body capability 解耦，并删除第二层 V/scalar-import 状态。

8.3 尚未成为正式 ISA

当前缺少最终合同：

  • B.SEQ；
  • B.PAR；
  • B.Z；
  • B.NZ；
  • P0..P7 的完整写入与保留规则；
  • EXEC save/update/restore；
  • reconvergence/control-stack 操作；
  • predicate spill/fill carrier；
  • B.PAR 的 memory/fault arbitration；
  • 0.59 object identity；
  • virtual TileOp 的最终 grammar 和默认反汇编视图。

B.Z 和 B.NZ 当前仅为 reserved-in-pto，不能因为已有 reservation encoding 就认为语义已经批准。

11. 实施顺序建议

建议拆成以下可评审提交：

  1. Typed body representation：去字符串化，但不改变现有输出；
  2. SIMT loop metadata：Clang pragma 与 IR metadata；
  3. Uniformity and structurization：只做分析和 remark；
  4. Control-flow target markers：增加 intrinsic/pseudo，不绑定物理编码；
  5. Tile region SSA：连接 LLVM #74；
  6. Subview/assemble CodeGen：复用已存在的物理 modifier；
  7. PAR legality verifier：实现 whole-body effect summary；
  8. Predicate virtual bank：PRED32、EXEC dependency 和压力检查；
  9. Accepted ISA lowering：等 PTO-SPEC #189 冻结后加入真实指令；
  10. MC/object/runtime closure：完成 0.59 发布链路。

每个阶段都应保持：

  • 0.58 legacy lane 可测试；
  • 0.59 experimental lane 不猜测物理语义；
  • 缺少目标 ISA capability 时明确拒绝；
  • 不用 inline assembly 绕过 LLVM 对控制流、predicate 和 region 的分析。

12. 最终结论

Issue #79 的目标合理，并且是从 0.58 body-local V 模型迁移到统一 0.59 SIMT 模型所必需的编译器重构。

当前可以先完成 typed IR/MachineIR、uniformity、控制流 marker、Tile region、B.SUBVIEW/B.ASSEMBLE 接入、B.PAR 合法性分析和诊断。当前不能完成最终物理 lowering，因为 PTO-SPEC #189 尚未冻结 B.SEQ/B.PAR、B.Z/B.NZ、predicate/EXEC、reconvergence、fault/restart 和 0.59 object identity。

实施原则应是：

先让编译器正确理解程序语义和依赖，再等待 ISA 给出物理承载；不得为了提前出汇编而恢复 body 字符串、暴露寄存器编号，或自行定义保留指令的语义。
