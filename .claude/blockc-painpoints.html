Block-C 编程体验痛点与遗留问题(开发人员参考)

调研基于 linx-llvm 编译器源码 + Linx-TileOP-API 头文件库 + SuperNPUBench 用法。 每条问题格式:现象 → 原理 → 当前怎么写(规避)。 所有问题有一条共同主线:目标地址空间 #6(__vbuf__ / addrspace(6),tile 缓冲区命名空间)。

主线:地址空间 6 (__vbuf__) 的根本机制

  • __vbuf__ 不是 clang 属性,而是 linx_blkc.h:8 的宏:#define __vbuf__ __attribute__((address_space(6)))
  • blkv_get_tile_ptr 经 Sema(SemaChecking.cpp:17965-17987)重写返回类型为 T addrspace(6)*
  • 后端靠地址空间区分 local/global 访问(LinxV5InstrInfoSIMT.td:726-738):
    • LoadAsLocal:getAddrSpace() == 6 → v.lb/lw/ld.local(tile 缓冲区本地访问)
    • LoadAsGlobal:getAddrSpace() != 6 → 全局 load
  • LinxV5TargetMachine.cpp:142-149 isNoopAddrSpaceCast 无条件返回 true:6→0 的 addrspacecast 被当 no-op

这条主线是问题 0、1、3、4 以及"__vbuf__ 丢失"的共同根因。

问题 0:cast 丢 __vbuf__ 静默生成 global load,编译器不报错

现象

SIMT __vec__ kernel 里,从 tile 取指针后做 C 风格 cast,如果漏写 __vbuf__:

__vbuf__ int64_t* keys_ptr = (__vbuf__ int64_t*)blkv_get_tile_ptr(query_keys); // ✓ 正确
int64_t* keys_ptr       = (int64_t*)blkv_get_tile_ptr(query_keys);             // ✗ 漏 __vbuf__

漏写时编译器静默接受,但生成的是 global load(v.ld 而非 v.ld.local),从错误的地址空间读 tile 数据,结果错误且极难排查。

原理

  • clang 的地址空间 cast 检查在 SemaCast.cpp:2548-2553(TryAddressSpaceCast)和 :2586-2600(checkAddressSpaceCast)——两处都被 if (OpenCL || SYCLIsDevice) 门控,普通 C/C++ 直接 short-circuit 返回 TC_NotApplicable,不做任何检查
  • DiagnoseCastQual(SemaCast.cpp:3203)只看 cvr(const/volatile),注释明确说地址空间是 "type identity" 不管
  • 叠加 isNoopAddrSpaceCast=true,6→0 cast 是 no-op,ISel 的 LoadAsGlobal PatFrag 匹配,出 global load
  • 现状:无任何诊断。所有测试都显式写 __vbuf__,没有"漏写报错"的负测试

当前怎么写(规避)

  • 每次 cast blkv_get_tile_ptr(...) 的结果,必须带 __vbuf__:(__vbuf__ T*)blkv_get_tile_ptr(tile)
  • 或用 auto*(auto 会保留 Sema 重写出的 AS6 限定符):auto* p = blkv_get_tile_ptr(tile);(但仍要确保后续 cast 不丢)
  • 不要写成 (T*)blkv_get_tile_ptr(...) 或 ((T*)blkv_get_tile_ptr(...))
  • tileop-api 内部统一用 BLKC_ASSIGN_PTR / BLKC_ASSIGN_CAST 宏(已硬编码 __vbuf__ T* 参数)

修复方向

在 Sema 的 C-style cast 路径加 LinxV5 专属诊断:源类型地址空间为 6(tile buffer)、目标非 6 时发 error/warning。挂在 checkAddressSpaceCast 或 SemaBuiltinBLKVGetTilePtr 之后的 use 处。

问题 1:低精度类型赋值/初始化必须用专用 API(blkc_assign_elem),operator= 不可用

现象

常规类型(float/int)加载/存储用 operator= 即可:

tile_ptr[index] = src[idx_gm];   // float/int OK

但低精度类型(__fp4_e1m2x2 / __int4x2 / __bf16x2 / __fp16x2 等)operator= 用不了,必须用专用 API:

BLKC_ASSIGN_CAST(dst_tile, idx, value);          // tile 句柄版
BLKC_ASSIGN_PTR(dst_ptr, idx, value);            // 已有 __vbuf__ 指针版
blkc_assign_cast(blkv_get_tile_ptr(dst), idx, v); // 直接调

原理

  • 低精度类型是 linx_blkc.h 里的 struct(包一个 data 成员),只定义了转换构造函数和转换 operator T()(DEFINE_CAST/DEFINE_SIMPLE_CASTS 宏,linx_blkc.h:51-91),没有用户定义 operator=
  • 隐式 copy-assign 是 raw 字节拷贝,对 sub-byte packed 类型不会生成 v.cvt,且在 addrspace(6) 上下文里 lowering 不对
  • 多个类型的 DEFINE_SIMPLE_CASTS 还被注释掉(linx_blkc.h:205,217,230,244,256,292),连转换路径都没有
  • blkc_assign_elem(TCvt.hpp:20-27)绕过 operator=,直接写 ptr[idx].data = value.data,且参数硬编码 __vbuf__ T*
  • 负测试 clang/test/LinxV5/blkv-e4m3-to-e5m2.cpp:7 确认跨类型 po[i] = pi[i] 报 no viable overloaded '='
  • 库内不一致:TCopyIn.hpp(load,:31,57,83,97,109...)和 TCopyOut.hpp(store,:30,55,104...)用 operator=(对低精度 dst 脆弱);TCvt.hpp 全用 BLKC_ASSIGN_PTR(:101,132,162...)

当前怎么写(规避)

  • 写 tile 元素赋值,低精度类型一律走 BLKC_ASSIGN_* 宏,不要用 ptr[i] = value
  • dst[i] = src[i] 同类型也尽量避开(隐式 copy-assign 行为不对);跨类型必用 BLKC_ASSIGN_CAST
  • 库开发者:新写 tile op 的 load/store/cvt kernel,统一用 BLKC_ASSIGN_PTR/CAST,不要直接 =

修复方向

(a) 给低精度 struct 加正确的 operator=(生成 v.cvt/正确宽度 store);(b) 统一 TCopyIn/TCopyOut 也走 blkc_assign_*;(c) 补定义 BLKC_ASSIGN_CAST_COMMON 或删除 TCvt.hpp:69 的引用(当前是潜在编译断裂)。

问题 2:返回值版本 vs 输出参数版本 API 不一致

现象

部分 block-compute API 有两个签名:返回值版用不了,只能用输出参数版:

__bf16 blkv_bf16_fmax(const __bf16&, const __bf16&);              // ✗ 用不了
void  blkv_bf16_fmax(__bf16& dst, const __bf16& l, const __bf16& r); // ✓ 只能用这个

原理

  • 头文件层(template_asm.hpp:1309-1341):宏其实同时生成两种形式——输出参数版 + 返回值版(返回值版内部调用输出参数版)。blkv_bf16_fmax 两版都在(:1424-1437)
  • clang builtin 层(BuiltinsLinxV5.def:20-29):只有一个名字、void 返回、variadic("v."),无 blkv_bf16_*,只有 blkv_max/blkv_fexp 等泛名
  • Sema 层(SemaChecking.cpp:4574-4588 CheckLinxV5BuiltinFPArith):要求参数 isRealFloatingType(),而 __bf16(=__blkc_bf16 struct)不是 real floating——直接被拒(err_linx_FPArith_invalid_type)
  • CodeGen 层(CGBuiltin.cpp:19320-19335):EmitLinxV5FPArith 其实是返回值版(无 dst 参数),但只对 fp32 等真浮点生效
  • 综合:fp32 可用 blkv_fexp(x) 返回值版;bf16 builtin 路径被 isRealFloatingType 拒,只能走头文件 inline-asm wrapper;返回值版虽存在但生成的临时 __bf16 不在 addrspace(6),流回 tile store 时又出问题,所以实际只能用输出参数版;bf16x2 同理

当前怎么写(规避)

  • bf16/bf16x2 的 fmax/fexp/fsqrt 等:用输出参数版 blkv_bf16_fmax(dst, l, r),不要用返回值版
  • fp32:blkv_fexp(x) 返回值版可用
  • 如需把结果存进 tile 元素,直接让 dst 是 tile 元素 lvalue,或先存局部再 BLKC_ASSIGN_*

修复方向

(a) 放宽 Sema 的 isRealFloatingType 判定,把 __blkc_bf16 等认作合法浮点;(b) 让 builtin 层支持低精度类型返回值版 CodeGen;(c) 头文件返回值版的临时对象地址空间问题单独修。

问题 3:类型转换部分需显式指定类型(linx_cvt_as<__fp8_e4m3x2>)

现象

有的转换能从参数推导,有的必须显式指定:

linx_cvt(p_new_ptr[src_idx], src0);              // ✓ bf16x2->hif4x2 可推导
linx_cvt_as<__fp8_e4m3x2>(upd_max);              // ✗ fp8 必须显式指定 Dst

原理

  • linx_cvt(Dst&, const Src&)(template_asm.hpp:723):Dst/Src 可从参数推导——只要有匹配的特化
  • linx_cvt_as<Dst>(const Src&)(:1151-1163):Dst 不在函数参数里,不可推导——任何类型都必须显式,不是 fp8 特有
  • fp8 额外摩擦:(i) _as6(addrspace 6)变体是手写固定签名重载(:992-1132),必须精确命名 __fp8_e6m2x2_as6 等;(ii) 部分 packed 类型(__fp4_*/__int4x2)的 DEFINE_SIMPLE_CASTS 被注释,隐式转换路径少,推导 fallback 少
  • LINX_DELETE_PACKED_SRC_TO_NORMAL_DST(:855-865)显式 delete 了某些 packed→normal 对

当前怎么写(规避)

  • 优先用两参数版 linx_cvt(dst, src),多数情况可推导(需 dst 是已类型化 lvalue)
  • linx_cvt_as<Dst>(src) 一律要写显式模板参数,这不是 bug 是签名决定
  • 涉及 __vbuf__ 目标时,用对应的 _as6 typedef(如 __fp8_e6m2x2_as6)

修复方向

(a) 给 linx_cvt_as 加推导代理(通过 Src 反推,或提供 linx_cvt_to<Dst>(src) 统一显式接口);(b) 用 if constexpr+traits 把 _as6 手写重载改成泛型模板;(c) 补全被注释的转换。

问题 4:不同数据类型 API 接口不一致,缺少类型推导

现象

同一算子,不同类型名字不同,无泛型模板:

blkv_fexp(x);            // fp32
blkv_bf16_fexp(dst, src); // bf16
blkv_bf16x2_fexp(dst, src); // bf16x2
// fp8/fp4/int4/fp16 —— 完全没有 wrapper

原理

  • ISA 助记符带类型后缀(.bf/.bfx2/.fb/.fh),BLKV_BF16_EMIT_*(template_asm.hpp:1242-1268)把后缀写死在 asm 串里
  • 每个类型的 data 成员宽度不同(char/short/int),asm 约束 "=vr" 需对应 LLVM 类型选寄存器类,*_STORAGE 宏(linx_blkc.h)逐类型展开
  • 所以 wrapper 用宏逐类型实例化(BLKV_DEFINE_BF16_* 只对 bf16/bf16x2 实例化),没有 BLKV_DEFINE_FP8_*/FP4_*
  • clang builtin 层只有一个泛名 blkv_fexp,LLVM intrinsic 按 arg 类型 overload,但 clang 名字固定

当前怎么写(规避)

  • bf16/bf16x2:用对应的 blkv_bf16_* / blkv_bf16x2_*
  • fp8/fp4/int4/fp16:走 linx_cvt / linx_cvt_as 转换路径,或自己写 inline asm
  • 不要期待统一的 blkv_fexp<T>

修复方向

可以用 if constexpr+storage<T> trait+类型→后缀映射写泛型 blkv_fexp<T>(非 ISA 硬性要求,是当前设计选择);为 fp8/fp4/int4/fp16 补 wrapper。

问题 5:复杂控制流——嵌套循环中的 break/continue 支持不完善

现象

hashfind 这类 __mtc__ kernel 有嵌套循环(外层 for idx += thread_num + 内层 for probe_cnt),内层带 break:

void __mtc__ hashfind(...) {
  for (int idx = tid; idx < num; idx += thread_num) {        // 外层
    ...
    for (int probe_cnt = 0; probe_cnt < max_probe; probe_cnt++) { // 内层
      if (curr_key == key_sentinel) { ...; break; }
      if (curr_key == key) { ...; break; }
    }
  }
}

单层 break/continue 已修(commit f637af5),但嵌套场景未验证、spill 处理有缺口,可能出现静默 miscompile。

原理

  • AnnotateControlFlow(注释 pass):Stack 是 LIFO,结构上能正确处理嵌套——外层 saved mask 压栈后,内层 push/pop 不破坏它;phi.broken 用 LI->getLoopFor(BB) 按当前 loop 作用域。handleLoop/closeControlFlow 对干净嵌套 for 不触发 assert/fatal。这一层 OK
  • ISelLowering:blkv_loop/blkv_if_break/blkv_end_cf 都是 depth-agnostic,只读写 SIMT_P 和各自 phi.broken SSA。嵌套 = 两套独立 phi.broken + 两套 save/restore,SSA 链排序即正确。这一层 OK
  • SIMTSpillFixup(缺口):fixupBlock 是逐 MBB、只跟踪单个 LastPBoundary(LinxV5SIMTSpillFixup.cpp:110-119)。没有"mask 边界栈"——嵌套循环体里,outer blkv_loop 写 P、inner blkv_if/blkv_loop 又写 P、inner end_cf 恢复、outer end_cf 恢复,fixup 只看到最后一个 P 写,会把 spill/reload 挪到"最后一个边界"前,可能跨过属于另一层 mask 区域的 Copy2P/Copy2PTerm,导致 spill 在错误的 active mask 下执行。getReasonBlocked(:85-106)只查中间内存/clobber/same-FI,不查是否跨了第二个叠加 mask 边界。症状:静默 miscompile(不崩溃)
  • 兜底:-linxv5-simt-spill-save-restore-p(LinxV5RegisterInfo.cpp:37-40,默认关)给每个 spill/reload 包 CopyFromP+SIMT_ORI_SCAR -1(P 置全 1)+Copy2P(恢复),使 spill 在任意嵌套 mask 下正确。代价:每次 spill/reload 多 3 条指令 + 共享 scratch T4(:50,递归 spill 展开时 reuse 无保护)
  • 测试缺口:llvm/test/CodeGen/LinxV5/Block-C/ 下所有 SIMT break/continue/spill 测试都只有单个 !llvm.loop,无嵌套 divergent loop 测试

当前怎么写(规避)

  • 嵌套 divergent loop + break/continue:加 -mllvm -linxv5-simt-spill-save-restore-p=true 编译选项兜底(确保 spill 在任意 mask 下正确)
  • 或尽量避免 divergent loop 嵌套 divergent loop(把内层 break 改写成单层循环 + 显式状态变量)
  • 降低寄存器压力以减少 spill 发生

修复方向

(a) 给 LinxV5SIMTSpillFixup 加per-block 边界栈,拒绝跨非栈顶边界的移动;(b) 或把 -linxv5-simt-spill-save-restore-p 设为 SIMT 默认(简单但费);(c) 加 simt-nested-break.ll 测试(hashfind 形状)+ simt-nested-spill-boundary.mir 回归保护。

问题 6:SIMT kernel 不支持返回值(blkv_rdadd 结果无法回流 scalar core)

现象

想在 __vec__ kernel 里 return 一个 vector reduce 结果给 scalar 调用方,支撑数据依赖的控制流:

int __vec__ probe_step_impl(...) {
  int64_t not_found = (...) ? 1 : 0;
  int64_t sum = blkv_rdadd(not_found);
  return sum;   // ✗ 返回值被静默丢弃,调用方拿不到
}
...
int r = probe_step_impl<<<...>>>(...);  // ✗ 不支持,表达式类型是 void

原理

  • 硬件/后端层(已具备):
    • blkv_rdadd lower 到 SIMT_RDADD(LinxV5InstrInfoSIMT.td:831-848),Dst 寄存器类 SIMTDstRegReduce = SIMT_DST_Scalar = SIMTCGSL ⊇ LTR/LUR = T1..T4/U1..U4 标量核 GPR——reduce 结果本来就写到标量核可读的 GPR
    • scalar 侧读回:int_linx_get_simt_ret(IntrinsicsLinx.td:40-42)→ lowerGetSIMTRet(LinxV5ISelLowering.cpp:1773-1781)→ CopyFromReg(getReduceDst(RetNo)),目标 GPR R2..R9(LinxV5RegisterInfo.cpp:75-82,最多 4 个)。跨侧数据通路完整
  • Clang 前端 + vcall IR 契约(缺口所在):
    • <<<>>> 在 Sema 被重写成 builtin __linx_vcall_par(SemaLinxBlockC.cpp:119),该 builtin 声明 "v."(void 返回,Builtins.def:675)——调用表达式类型恒为 void,int r = foo<<<...>>>(...) 直接类型错
    • vcall intrinsic int_linx_vcall_par 的 RetTypes 是 TileCallRetsBuilder<onum> = onum 个 llvm_anyvector_ty(只 tile/vector 输出,无标量,IntrinsicsLinx.td:136-158),onum 只数 __out__ tile 参数,不含 C 返回
    • CodeGen parseLinxVCallIntID/Params(CGBuiltin.cpp:686-761)只从 LinxBLKFuncOutAttr tile 参数填 Rets,C 返回值**从不进 Rets**;emitLinxVCallInt(:763-799)只把 vcall ret 存到 __out__ lvalue
    • Sema handleLinxBLKFuncAttr(SemaDeclAttr.cpp:8060-8075)不检查返回类型,非 void __vec__ 声明被接受(测试 linx-single-layer.c:9,13 证明默认模式接受 __vec__ int),但返回值被静默丢
    • linx_get_simt_ret 在 LLVM target 里有,但 clang 没 expose 成 builtin(Builtins.def/BuiltinsLinxV5.def 无条目,CGBuiltin 无 case),用户从 C 无法命名

当前怎么写(规避)

  • 不要用 __vec__/__mtc__ kernel 的返回值——当前被丢弃
  • 要把 reduce 结果传给 scalar 调用方:用 tile __out__ 参数承载结果(支持的 vcall 输出通道),scalar 侧从 tile 读
  • 或在 SIMT 区内直接 blkv_rdadd,scalar 侧通过其他已支持的机制读 GPR(目前无直接 builtin,需等 linx_get_simt_ret expose)

修复方向

  1. Sema(ActOnLinxBlockCCall):根据被调函数返回类型,在调用侧分配结果 lvalue,传入 builtin
  2. Builtin:__linx_vcall_par 加非 void 变体,或不走 void builtin、直接建 llvm.linx.vcall.par.<N>d<M>u 调用并把标量返回纳入 RetTypes
  3. Intrinsic:TileCallRetsBuilder 增加标量返回槽,或调用侧 vcall 后发 linx_get_simt_ret(<ret index>)(目标 GPR 已是 R2..R9)
  4. CodeGen:检测非 void __vec__/__mtc__ 被调,vcall 后 emit linx_get_simt_ret 读回并绑定到调用方 lvalue(后端 lowerGetSIMTRet/getReduceDst 已支持)
  5. kernel 侧:return sum(已是 blkv_rdadd 输出,已在 R2..R9)关联到该 GPR 槽
  6. 诊断(过渡期):handleLinxBLKFuncAttr 对非 void 返回报错,提示用 tile __out__ 或 blkv_rdadd+linx_get_simt_ret,避免静默丢

一句话总结(给开发人员)

当前 Block-C 语法上还没支持的写法,以及怎么规避:

  1. __vbuf__ 不能漏——cast blkv_get_tile_ptr 结果必须带 __vbuf__(漏了静默出 global load,编译器不报错)。
  2. 低精度类型不能用 = 赋值——__fp4_*/__int4x2/__bf16x2 等 tile 元素赋值必须用 BLKC_ASSIGN_CAST/BLKC_ASSIGN_PTR,不要写 ptr[i]=value。
  3. bf16 算子只能用输出参数版——blkv_bf16_fmax(dst,l,r),返回值版 __bf16 r=blkv_bf16_fmax(l,r) 用不了。
  4. linx_cvt_as<Dst> 必须显式指定目标类型——两参数 linx_cvt(dst,src) 能推导,单参数 linx_cvt_as 不行。
  5. 没有泛型 blkv_fexp<T>——fp32 用 blkv_fexp,bf16 用 blkv_bf16_fexp,fp8/fp4/int4/fp16 无 wrapper,走 linx_cvt。
  6. 嵌套循环 break/continue 加兜底选项——divergent loop 套 divergent loop 时加 -mllvm -linxv5-simt-spill-save-restore-p=true,否则可能静默 miscompile。
  7. __vec__/__mtc__ kernel 返回值被丢弃——不要 return 值给 scalar 调用方;reduce 结果走 tile __out__ 参数传出。

遗留 bug 清单

  • TCvt.hpp:69 BLKC_ASSIGN_CAST_COMMON 引用但无定义(潜在编译断裂)
  • __fp4_*/__int4x2/__fp16x2/__bf16x2 的 DEFINE_SIMPLE_CASTS 被注释(linx_blkc.h:205,217,230,244,256,292)
  • fp8/fp4/int4/fp16 无 blkv_*_<op> wrapper
  • LinxV5TargetMachine::isNoopAddrSpaceCast 无条件 true,放大了问题 0
  • LinxV5SIMTSpillFixup 无嵌套 mask 边界栈,嵌套 divergent loop spill 可能 miscompile(问题 5)
  • __vec__/__mtc__ kernel 返回值静默丢弃,无诊断(问题 6);linx_get_simt_ret 未 expose 成 clang builtin
  • -linxv5-simt-spill-save-restore-p 默认关,共享 scratch T4 递归 reuse 无保护

三条系统修复主线

  1. __vbuf__/addrspace(6) 的诊断缺失(问题 0):cast 丢限定符静默出错,应加 Sema 诊断。最易踩、最难查,优先级最高。
  2. 低精度类型的 operator= 缺失(问题 1、2、3 共因):struct 没有正确 operator=,导致 TCopyIn/Out 用 operator= 脆弱、blkc_assign_* 硬编码 AS6、linx_cvt 手写 _as6 重载、返回值版临时对象地址空间错。统一修 operator= 能消解一大片。
  3. API 泛型化不足(问题 2、3、4):类型特定名字 + 手写重载,可用 if constexpr+traits 统一,减少 blkv_<type>_<op> 爆炸和 linx_cvt_as 必须显式。
